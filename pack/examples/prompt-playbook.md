# Prompt Playbook — Marisol's Kitchen
Standing rules for how we work. Applies to every session.

## The four-part prompt (use for every non-trivial request)
1. **Context** — what exists right now ("The hero on index.html currently…")
2. **Goal** — what I want ("…fit on two lines on a phone…")
3. **Constraints** — what must not change ("…keep the copy exactly as written…")
4. **Success criteria** — how I'll judge it ("…done when it fits at 375px with no awkward wrap")

## Habits
- One change per prompt. Batches allowed only for one *kind* of change (e.g., ten copy fixes).
- Describe the observable problem, not a guessed solution.
- Screenshots over paragraphs. Point at files by name.
- Explain before editing; plan before big changes ("plan first — don't write code yet").
- The loop: look → describe → prompt one change → verify → commit.

## Model roles (never version names — see Appendix F / repo for current lineup)
| Role | Use for |
|---|---|
| Flagship + extended thinking | Architecture, tricky debugging, pre-launch security review |
| Workhorse (default) | Features, design iteration, CMS wiring, structured drafting |
| Efficient + low thinking | Copy tweaks, alt text, renames, proofreading, brainstorm lists |

## Escalation ladder
1. Start one rung lower than you think you need.
2. Escalate on failure, not anxiety: two flubs → one rung up, re-run the SAME prompt.
3. Drop back down after the hard part.
4. Three failed iterations → stop; escalate with extended thinking; ask for DIAGNOSIS AND PLAN, not another attempt.

## Conservation rules
- Plan on paper (or a cheap chat) before burning agent turns.
- Fresh session per task; compact when long.
- Targeted edits over full-file rewrites.
- These context files carry standing instructions — never re-explain the project.
- Maximum everything is a spending setting, not a quality setting.
